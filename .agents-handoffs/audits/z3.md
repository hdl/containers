## Root-cause hypothesis

**Recipe vs. upstream master regression (C++20 requirement) — not test, not runtime-deps, not environment.**

- The failing construct is **parenthesized aggregate initialization** (C++20 P0960R3): upstream rewrote the anonymous-struct union member of `tp_elem` from member-wise init to a named member aggregate initialized with parens:
  - before: `struct { enode * m_lhs; enode * m_rhs; }; … :m_kind(EQUALITY), m_lhs(lhs), m_rhs(rhs) {}` → valid C++14/17.
  - now:  `struct { … } m_pair; … :m_kind(EQUALITY), m_pair(lhs, rhs) {}` → requires clang ≥ 16 / gcc ≥ 10 (P0960).
- The change is upstream Z3 commit `b902c020ced4` "Fix uses of gnu anonymous structs. (#10345)", merged 2026-08-01, and is **already in the latest stable tag `z3-5.1.0`** (verified via raw file). All 4.x tags (`z3-4.14.1`, `z3-4.15.8`, `z3-4.16.0`) still use the member-wise form and compile cleanly with clang 11.
- **Proven in the exact build container**: `clang++ -std={c++14,c++17,c++20} -fsyntax-only` on a minimal reproduction of `T(int x,int y):m(x,y){}` with a nameless-aggregate member reproduces the **identical diagnostic** ("no matching constructor … implicit copy constructor … requires 1 argument, but 2 were provided") in every standard mode. clang 11 simply never learned P0960 (landed in clang 16); no `-std=` flag can unlock it.
- bullseye EOL apt is not a factor: `apt-get update/install` in step 2/3 succeeds (snapshot.debian.org pinning works), so this is purely a toolchain-vs-upstream incompatibility.

## Recommended next step

The recipe cannot keep cloning unpinned master for the bullseye (clang 11, no gcc) toolchain. Options, in order of preference:

1. **Pin the recipe to a compatible upstream point** (most robust, matches pono/pinned-commit pattern): commit to a specific `Z3Prover/z3` commit or tag that is still clang-11-clean — any of the `4.x` tags (e.g. `z3-4.16.0`, `git checkout <tag>`) — while leaving a `git checkout z3-5.1.0`… no: `5.1.0` is already affected, so pin ≤ `4.16.0` (or the last pre-`b902c020ced4` master commit). Update `debian/z3/HDLC:34-36`.
2. **Provide a C++20 compiler in makedepends**: bullseye's `clang-12`/`clang-13` are still too old for P0960, and no clang-16 exists for bullseye; the only viable in-archive compiler would be GCC 10 (`gcc`/`g++`, which support P0960) **plus** a way to force Z3's `mk_make.py` to use it (e.g. `--gcc=true`/`--cxx=g++-10`), since it currently auto-picks clang. More invasive and leaves other C++20 uses in master at risk.
3. **Re-wire the task to a newer collection** for a newer clang — not possible for this z3 lane (`SysDebianLegacyAmd64` is bullseye-only by design), and Z3 master itself would still need clang ≥ 16.

Whichever path, re-run this audit command; `pkg/z3` must reach `=== PASS pkg/z3 ===`, which requires `BuildImage(..., test=True)` to complete — i.e. `test/z3.pkg.sh` running through the `testpkg` wrapper (currently untested because the build aborts).
